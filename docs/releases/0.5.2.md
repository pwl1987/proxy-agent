# 0.5.2 — Web / LAN Management Plane

## Release status

- Branch: `release/0.5.2`
- Baseline: accepted 0.5.1
- Release type: remote management surface
- Implementation status: blocked until 0.5.1 is accepted

## Goal

Expose the existing Control API v1 through a secure authenticated HTTPS Web Gateway without creating a second control state machine.

## In scope

1. Authenticated HTTPS management listener.
2. Web Gateway calls Control API v1; no direct backend or state-file control.
3. Explicit management listener binding and LAN ACL.
4. Session lifecycle, logout/revocation, secure cookie/token handling and login-rate limiting.
5. CSRF protection for browser state changes.
6. One Admin role; complex RBAC is deferred.
7. Profile/backend/Egress Path configuration UI driven by typed/capability metadata.
8. Validate -> Diff -> Apply using existing optimistic concurrency.
9. Health, event, audit and revision views using Control API data.
10. Explicit remote-mutation audit durability semantics.
11. Explicit Web Gateway -> protected local Control API access design; the existing 0600 socket must not be weakened as a shortcut.

## Explicit non-goals

- Public SOCKS/HTTP management shortcut.
- Direct editing of config, runtime or revision files.
- Direct systemctl/backend lifecycle control from Web.
- Parallel revision, audit or reconcile implementation.
- Full RBAC.
- SSO/OIDC.
- Universal zero-downtime activation.
- Traffic inspection or censorship/DPI evasion.

## Real-code impact review required

The Web path must be verified as:

```text
Browser
  -> HTTPS Web Gateway
  -> Control API v1
  -> existing authz/mutation contract
  -> revision + audit + desired state
  -> existing reconciler/lifecycle
  -> backend
```

The Web layer is presentation/authentication/transport only. It must not become a second source of truth.

## Acceptance criteria

### A. Security boundary

- Unauthenticated mutation is rejected.
- Session/token lifecycle is revocable.
- CSRF protections cover state-changing browser requests.
- Login abuse is rate-limited.
- Cookies/tokens use secure defaults.
- LAN ACL behavior is deterministic and tested.
- Private-key material and secret contents never reach the browser.

### B. Control API reuse

- Web reads and mutates only through Control API v1.
- Existing optimistic concurrency behavior is preserved.
- Stale edits return the existing revision-conflict semantics.
- Web does not bypass revision, audit, lifecycle or upgrade locks.

### C. Audit durability

- A remote mutation that requires durable audit does not report success when its audit record cannot be committed.
- Actor attribution is present without recording secrets.
- Audit failures have stable machine-readable error semantics.

### D. UI/data contract

- Forms follow typed configuration and capability metadata.
- Unsupported backend capabilities cannot be configured accidentally.
- Validate -> Diff -> Apply is explicit; no hidden immediate activation from form edits.
- Health and revision views distinguish desired/observed state and causal failures.

### E. Deployment

- Supported system/rootless/container modes have explicit gates.
- The local Control API socket remains protected.
- No listener is opened publicly by default.

### F. Testing

- Authentication/session/CSRF/rate-limit tests.
- ACL and protected-socket access tests.
- Concurrent-edit/revision-conflict tests.
- Audit failure/durability tests.
- Web-to-Control-API contract tests.
- Full accepted 0.5.1 regression suite.

## Release exit gate

0.5.2 is complete only when the complete 0.5.1 gate passes and the Web/LAN management surface cannot bypass the established control-plane ownership or security boundaries.
