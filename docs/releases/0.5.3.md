# 0.5.3 — Recovery / Operations

## Release status

- Branch: `release/0.5.3`
- Baseline: accepted 0.5.2
- Release type: recovery and operational completeness
- Implementation status: blocked until 0.5.2 is accepted

## Goal

Make configuration recovery, export/import and operational diagnosis safe, reproducible and compatible with the existing revision/audit/reconcile/lifecycle model.

## In scope

1. Canonical configuration/revision export.
2. Import with explicit parse, schema/semantic validation and compatibility checks.
3. Recovery flow: validate -> compatibility check -> create revision -> explicit apply.
4. Private-key contents excluded from exports and normal diagnostics.
5. Richer diagnostics and event visibility using existing state/control contracts.
6. LAN deployment/integration coverage for the already-accepted management plane.
7. Upgrade/downgrade compatibility documentation and tests.
8. Bounded recovery state with attempt budget, backoff, stable terminal reason and reset/recovery condition.

## Explicit non-goals

- Automatic multi-egress failover.
- Load balancing.
- Connection draining.
- New proxy topology beyond the accepted 0.5.1/0.5.2 contracts.
- Full RBAC or SSO.
- Direct runtime-state import as an activation shortcut.
- Silent migration that changes semantics without an explicit compatibility decision.

## Real-code impact review required

Recovery must trace the actual control path:

```text
exported canonical config/revision
  -> parser
  -> schema + semantic validation
  -> compatibility/migration check
  -> revision creation
  -> optimistic-concurrency decision
  -> audit
  -> explicit desired state
  -> reconciler
  -> observed runtime state
```

Import must not create a parallel activation path or bypass revision/audit/lifecycle/upgrade locks.

## Acceptance criteria

### A. Export safety

- Export contains canonical configuration/revision metadata and supported references.
- Export excludes private-key contents, PIDs, sockets, transient process state and transient health.
- Exported data is sufficient to reconstruct a supported configuration through the normal import flow.

### B. Import safety

- Malformed data fails before revision creation.
- Schema/semantic incompatibility fails before activation.
- Unsupported newer schema versions are reported explicitly; they are never silently downgraded.
- Successful import creates normal revision history.
- Activation remains an explicit operation; no implicit activation occurs merely because import succeeded.

### C. Compatibility

- Supported 0.4.x and 0.5.x configuration compatibility expectations are documented and tested.
- Downgrade behavior is explicit and tested for supported cases.
- Migration does not bypass audit or revision concurrency.

### D. Recovery/self-healing

- Recovery retries are bounded.
- Backoff and retry state are observable.
- Terminal failure is stable and operator-visible.
- Recovery does not recursively create an unbounded restart loop.
- A defined reset/recovery event clears terminal recovery state safely.

### E. Operations

- Diagnostics distinguish validation, revision, transport, backend, reconciliation and deployment failures.
- Event/audit/revision views remain consistent with existing Control API v1 semantics.
- No second operational truth store is introduced.

### F. Testing

- Export/import round-trip tests.
- Secret redaction tests.
- Invalid/incompatible import tests.
- Revision/audit/lifecycle bypass regression tests.
- Upgrade/downgrade compatibility tests.
- Bounded recovery and terminal-state tests.
- System/rootless/container integration tests where supported.
- Full accepted 0.5.2 regression suite.

## Release exit gate

0.5.3 is complete only when the complete 0.5.2 gate passes and recovery is demonstrably safe, bounded, reproducible and compatible with the canonical control-plane contracts.
