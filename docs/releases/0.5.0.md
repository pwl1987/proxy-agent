# 0.5.0 — Egress Path Foundation

## Release status

- Branch: `release/0.5.0`
- Baseline: 0.4.x verified `main`
- Release type: architecture foundation
- Implementation status: not started; contract frozen first

## Goal

Introduce a canonical Egress Path contract and direct transport semantics without changing established 0.4.x runtime behavior.

## In scope

1. Add the typed `egress_path` model needed for a single direct path.
2. Define Backend vs Egress Path ownership in the real config/reconcile/backend call chain.
3. Support `direct` semantics with an explicit target representation.
4. Preserve legacy `ssh-socks` configuration when `egress_path` is absent.
5. Reject ambiguous/conflicting legacy + new target definitions deterministically.
6. Keep typed configuration/revision canonical and project to legacy runtime configuration one-way.
7. Define route -> Egress Path resolution without implementing multi-egress selection.
8. Wire revision/reconcile behavior so a path change follows the existing desired/observed and lifecycle boundaries.
9. Add focused schema, validation, revision, reconcile and regression tests.

## Explicit non-goals

- SSH Jump Host runtime.
- Web or LAN management.
- Secret-provider framework.
- Export/import.
- Connection draining.
- Automatic failover, balancing or multi-egress selection.
- New parallel state store or Web-specific state machine.

## Real-code impact review required before implementation

The implementation must trace and record the actual repository path through:

```text
typed config/schema
  -> profile resolution
  -> validation
  -> revision snapshot
  -> reconcile desired/observed state
  -> legacy/runtime projection
  -> ssh-socks backend
  -> route resolution
  -> runtime/health state
  -> Control API exposure
```

Existing SSH process ownership, PID/listener checks, keepalive and lifecycle behavior remain authoritative; 0.5.0 must not duplicate them.

## Acceptance criteria

### A. Compatibility

- Every applicable 0.4.x smoke/contract suite remains green.
- Existing profiles without `egress_path` behave identically to the verified 0.4.x behavior.
- Existing `REMOTE_HOST`, `REMOTE_USER`, `REMOTE_PORT`, `REMOTE_SSH_KEY` semantics remain valid where currently supported.

### B. Validation

- Valid direct Egress Path configurations are accepted.
- Invalid/missing required target data is rejected with stable machine-readable errors.
- Conflicting legacy and Egress Path target definitions are rejected; no last-write-wins behavior.
- Unsupported backend/capability combinations fail explicitly.

### C. State/concurrency

- New configuration enters the existing revision model; no second revision store is created.
- `current_revision`, `desired_revision`, `observed_revision` semantics remain unchanged.
- Existing revision/audit/lifecycle locks remain authoritative.
- Reconciliation remains pinned to the requested revision.

### D. Runtime

- Typed config is projected to legacy runtime config in one direction only.
- No duplicate Egress Path state file is introduced.
- Existing managed backend ownership/liveness tests remain green.

### E. Testing

- Schema/validation tests cover valid, invalid and conflicting configurations.
- Regression tests cover legacy profiles.
- Reconcile tests cover successful projection and activation failure without corrupting revision state.
- Control/API regression tests confirm no existing 0.4.x contract is broken.

## Release exit gate

0.5.0 is complete only when the full previous-release gate plus every acceptance criterion above passes and the implementation/documents do not require any unfinished 0.5.1+ feature.
