# 0.5.2 Web/LAN Management Plane：Gateway Foundation

## 当前切片

本切片只建立 Web/LAN 管理面的安全入口，不引入第二套控制面逻辑。

```text
Browser / operator
        │
        ▼
Authenticated Web Gateway
        │
        ▼
local Control API v1
        │
        ├── revision
        ├── audit
        ├── desired / observed
        ├── reconciler
        └── backend lifecycle
```

Gateway 只负责 transport、认证边界和请求转发；revision、audit、apply、rollback、reconcile、backend lifecycle 继续由既有 Control API v1 负责。

## 安全边界

- 默认监听 `127.0.0.1`。
- `/healthz` 是 Gateway 自身存活探针，不暴露控制面数据。
- Control API 默认继续通过 Unix socket 访问。
- 管理 API 请求必须携带 `Authorization: Bearer <admin-token>`。
- 非 loopback listener 必须同时启用 TLS 1.2+ 证书/私钥；禁止无 TLS 的 LAN 管理入口。
- 所有代理响应使用 `Cache-Control: no-store`。
- 本切片只代理既有 read API，不开放 mutation；写操作将在 session/CSRF/optimistic-concurrency 边界冻结后接入。
- Gateway 不读取 revision store、audit store、runtime state，也不直接控制 backend 进程。

## 第一阶段路由

允许只读转发：

```text
GET /api/v1/status
GET /api/v1/health
GET /api/v1/metrics
GET /api/v1/capabilities
GET /api/v1/config
GET /api/v1/events
GET /api/v1/revisions
GET /api/v1/revisions/{revision}
```

其他路径返回 `404`；所有 mutation 方法当前返回 `405 read_only_gateway`。

## 下一切片

后续按以下顺序扩展：

1. Admin session 生命周期、Secure/HttpOnly/SameSite cookie、CSRF token。
2. 登录 rate limit 与认证失败审计。
3. management listener + LAN ACL 配置模型。
4. Web mutation 映射到 Control API v1：`validate → revision → apply`。
5. optimistic concurrency conflict UI。
6. profile/backend/egress/health/revision/event 页面。

任何一步均不得创建第二套 revision、audit、reconcile 或 lifecycle 状态机。
