# 0.5.x Release Governance

> Status: frozen engineering rule for the 0.5.x evolution line.
>
> Purpose: make every 0.5.x minor release independently buildable, testable, reviewable and rollbackable, while preventing a later release from silently damaging an earlier release contract.

## 1. Release branch model

Each release has its own branch:

```text
release/0.5.0
release/0.5.1
release/0.5.2
release/0.5.3
```

`main` represents the latest accepted stable integration point. A release branch is the only branch on which that release's implementation scope is developed.

The branch is created only from an accepted stable baseline. Future releases may have their requirement branches created early for contract planning, but implementation must not depend on unfinished future releases.

## 2. Scope-before-code rule

Every release must have its own scope and acceptance contract before implementation starts. The contract must define:

- Goal and user-visible outcome.
- In-scope implementation items.
- Explicit non-goals / forbidden scope creep.
- Affected modules and dependency/call-chain boundaries.
- Data/state ownership changes.
- Compatibility obligations.
- Regression suite and new acceptance tests.
- Release exit criteria.

A feature that is not in the release contract is not added merely because it is convenient while implementing another feature. It becomes a candidate for a later release or requires an explicit decision-record update before work starts.

## 3. No silent damage to the previous release

For every release `N+1`:

```text
release N acceptance suite
        +
release N+1 new acceptance suite
        =
release N+1 release gate
```

The previous release's frozen behavior is the compatibility baseline. Breaking changes require an explicit decision record, migration/compatibility plan and a corresponding version boundary; they must never enter as an accidental side effect.

## 4. Preferred change direction

Prefer additive, capability-gated, profile-scoped changes:

```text
existing contract
    -> additive field/capability
    -> explicit validation
    -> existing revision/reconcile/lifecycle path
```

Avoid parallel sources of truth, parallel state machines, direct file mutation from upper layers, backend-name conditionals when a capability can express the feature, and silent semantic changes to existing fields.

## 5. Upstream synchronization rule

When a defect is found after a release branch has been accepted, first classify it:

- Existing-baseline defect: fix at the lowest affected supported release boundary, then propagate forward.
- New-feature defect: fix only in the release that introduced it, then propagate forward when appropriate.
- Intentional breaking behavior: update the decision record and migration/compatibility contract before implementation.

Do not use a later release as the only place to repair a regression that already existed in an earlier supported release.

## 6. Mandatory release gate

A release cannot be declared complete until all applicable gates pass:

1. Full regression suites from the previous accepted release.
2. New unit/schema/contract/smoke tests for the release scope.
3. Configuration compatibility checks.
4. Revision/concurrency/audit/lifecycle regression checks.
5. Profile isolation checks.
6. Health/reconcile/recovery checks relevant to the release.
7. System/rootless/container deployment checks relevant to the release.
8. ShellCheck and existing repository quality gates.
9. Documentation consistency: implementation, API/state docs, roadmap and decision records agree.

## 7. Canonical ownership rule

Release work must preserve the existing ownership model:

```text
Typed Config / Revision
        -> Reconciler
        -> Runtime projection
        -> Backend / Adapter
```

Control API remains the control contract. Runtime facts remain in runtime state. Desired/observed convergence remains in reconciliation state. Audit, revision, lifecycle and upgrade locks remain authoritative. Web is a future client surface, not a second control engine.

## 8. Version boundaries for 0.5.x

| Release | Contract | Explicitly not included |
|---|---|---|
| 0.5.0 | Egress Path foundation and direct transport | Web, LAN management, Jump runtime, secret-provider framework, export/import, draining, failover/balancing |
| 0.5.1 | One-hop SSH Jump, identities, host-key references, path health | Web, LAN management, multi-hop DSL, automatic failover/balancing |
| 0.5.2 | Authenticated Web/LAN management over Control API v1 | Public SOCKS/HTTP management shortcut, full RBAC, SSO/OIDC, universal zero-downtime |
| 0.5.3 | Recovery, export/import, compatibility and operations | Automatic failover/balancing, broad new runtime topology |
| 0.5.4+ | Advanced runtime capabilities | Any capability without explicit semantics, tests and feature gating |

## 9. Definition of done

A release is done only when its branch can be described by all of the following:

- The scope is explicit and closed.
- The implementation follows the frozen architecture and ownership boundaries.
- The prior release remains green.
- New acceptance tests prove the new behavior and failure cases.
- State transitions, concurrency and recovery are deterministic.
- Unsupported capabilities fail explicitly rather than silently degrading.
- Documentation matches the shipped behavior.
- The branch can be merged to `main` without requiring unfinished future-release code.

## 10. Default development flow

```text
Stable main
  -> release/0.5.N
  -> freeze scope + acceptance
  -> trace real code / call chain / state ownership
  -> write tests
  -> implement
  -> full previous-release regression
  -> release-specific acceptance
  -> documentation consistency check
  -> merge to main
  -> tag v0.5.N
  -> next release branch
```
