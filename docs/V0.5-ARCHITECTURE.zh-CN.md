# 0.5.x Architecture Decisions

> Status: architecture freeze candidate. This document defines the design boundaries for the whole 0.5.x evolution line; individual releases implement only their declared scope.
>
> Baseline: `main` at `932bc691a13b94abbe74bcdba7e6b498971305ed`.
>
> Core rule: freeze concepts, ownership, state semantics, compatibility rules and extension points early; deliver implementation incrementally as `0.5.0`, `0.5.1`, `0.5.2`, `0.5.3`, then `0.5.4+`.

## 1. Version strategy

0.5.x is one architectural evolution line, not one oversized feature release. Every release must be independently buildable, testable and rollbackable within the supported deployment boundary.

### 0.5.0 — Egress Path foundation

- canonical Egress Path model and validation
- Backend vs Egress Path ownership boundary
- direct transport semantics
- legacy `ssh-socks` compatibility when Egress Path is absent
- typed-config to legacy-runtime projection rules
- route -> egress resolution contract without multi-egress selection
- focused schema/revision/reconcile regression coverage

No Web, LAN public management, Jump Host, secret provider framework, export/import, failover or draining implementation is required.

### 0.5.1 — SSH Jump, identity and path-health foundation

- one-hop Local -> Jump -> Target SSH transport
- independent Jump and Target identity references
- secret/known-host reference abstraction and minimum file-backed implementation
- path-level health and evidence/reason semantics
- explicit DNS path policy, preserving current `ssh-socks` remote-DNS behavior by default
- transport/Jump/Target diagnostics

The existing `ssh-socks` lifecycle, process ownership and liveness checks remain the runtime foundation.

### 0.5.2 — Web/LAN Management Plane

- authenticated HTTPS management listener
- Web Gateway as a client of Control API v1
- session, CSRF, login-rate-limit, secure-cookie/token and ACL boundaries
- profile/backend/egress configuration UI
- validate -> diff -> apply flow with optimistic concurrency
- health/event/revision views

Web never directly edits runtime files, invokes backend lifecycle commands, owns revision/audit state or implements reconciliation.

### 0.5.3 — Recovery and operational completeness

- configuration/revision export/import
- validate-before-activation recovery
- richer diagnostics and event visibility
- LAN deployment/integration coverage
- documented upgrade/downgrade compatibility behavior

### 0.5.4+ — Advanced runtime capabilities

- connection draining behind explicit backend capability
- multiple named Egress Paths
- route -> Egress selection
- future EgressGroup abstraction
- health-driven failover/balancing only after separate failure-policy semantics are specified and tested

The exact patch/minor sequence may change with implementation evidence, but the architectural ordering and non-goals remain stable unless a new decision record explicitly supersedes them.

## 2. Architecture layers and ownership

The system is divided into four layers:

```text
Domain Contract
  Backend / Egress Path / Transport / Identity / Route / Profile
        |
Control Contract
  Revision / Desired+Observed / Audit / Health / Capability / API
        |
Runtime + Deployment
  Reconciler / lifecycle / locks / systemd / rootless / container
        |
User Surface
  CLI / TUI / Web / LAN
```

Upper layers must use lower-layer contracts and must not create parallel implementations of lower-layer responsibilities.

### Backend

Backend means **what proxy implementation is running**. It owns backend-specific lifecycle, endpoint, ownership and capabilities.

### Egress Path

Egress Path means **how a backend reaches its upstream/target**. It is a domain contract, not a replacement backend.

### Transport

Transport is the path mechanism used by an Egress Path. In early 0.5.x it is a domain contract implemented inside the existing backend where practical; do not create a separate transport daemon merely for abstraction purity.

### Route

Route decides traffic policy (`DIRECT` vs proxy/action). It must not own SSH transport details or secret resolution.

### Profile

Profile remains the isolation boundary for configuration, runtime state, logs and revision history. New Egress Path and identity references are profile-scoped unless a future explicit shared-resource model is introduced.

## 3. Canonical configuration and projection

Typed configuration is the sole canonical configuration model and revision payload:

```text
Typed Config / Revision
        |
        v
Validation
        |
        v
Reconciler
        |
        v
Legacy Runtime Config
        |
        v
proxy-ctl / backend / adapter
```

Legacy configuration is a compatibility/runtime projection, never a second source of truth. No bidirectional typed <-> legacy synchronization is permitted.

When `egress_path` is absent, existing backend-specific configuration such as `REMOTE_HOST`, `REMOTE_USER`, `REMOTE_PORT` and `REMOTE_SSH_KEY` remains valid. A configuration containing both legacy target fields and an Egress Path with conflicting meaning must fail validation rather than silently choosing one.

This preserves 0.4.x behavior while giving 0.5.x a migration path.

## 4. Egress Path model

The conceptual model is:

```yaml
egress_path:
  transport: ssh
  mode: direct | jump
  target:
    host: ...
    port: ...
    user: ...
    identity_ref: ...
    known_hosts_ref: ...
  jump:
    host: ...
    port: ...
    user: ...
    identity_ref: ...
    known_hosts_ref: ...
  dns_mode: local | remote
```

The model is deliberately a domain contract, not a promise that every field is implemented in 0.5.0.

Rules:

- `direct` has a target and no jump.
- `jump` requires exactly one jump and one target.
- 0.5.x initial Jump support is one hop only: Local -> Jump -> Target.
- Raw SSH `ProxyJump` command strings are not the primary configuration model.
- Backend-specific invocation details are generated from the domain model.
- The final target is distinct from the browser/client destination.

### Future multi-egress evolution

Do not make 0.5.0 carry a full registry/selection engine. The Egress Path object must remain reusable when later represented as:

```text
Profile
  egress-us
  egress-jp
  egress-sg
```

and eventually:

```text
Route decision
   -> Egress selection
      -> named Egress Path
```

The object contract is frozen earlier than the container/selection policy.

## 5. Jump Host and transport boundary

The default topology is:

```text
proxy-agent
   |
   | SSH transport
   v
Jump Host (OpenSSH)
   |
   | forwarding
   v
Target
```

The Jump Host does not run another `proxy-agent` in 0.5.x. It is a network path node. A dedicated agent is only justified later if the intermediate node becomes a policy/accounting/failover/VPN/NAT/multi-egress control point.

Existing `ssh-socks` lifecycle and process identity checks remain authoritative for the managed SSH backend. Egress Path work must not duplicate PID ownership, listener ownership, keepalive or host-key lifecycle logic.

## 6. Identity, secrets and known hosts

Identity is referenced logically:

```text
identity_ref
known_hosts_ref
```

The reference is not secret material and must not encode a provider-specific implementation detail into the Egress Path contract.

Runtime resolution is:

```text
reference
  -> existence/readability/permission validation
  -> runtime resolution
  -> transport/backend
```

The first implementation may be file-backed. Future keyrings or external secret stores can implement the same resolver contract.

Jump and Target identities are independently addressable. Reusing one identity is allowed only when explicitly configured; it is not a hidden global default.

Private-key material must never appear in Web responses, revision payloads, audit events or exports. Fingerprints/configured state/validation status may be exposed.

Host-key verification policy is separate from known-host material. Strict verification remains the default for SSH transports.

## 7. DNS semantics

DNS path is part of Egress Path behavior, not a hidden side effect of a UI.

Minimum policy:

```text
dns_mode: local | remote
```

Existing `ssh-socks` uses `socks5h`; its remote-DNS behavior is preserved by default. A future DNS implementation must remain diagnosable as part of the selected path.

No separate DNS daemon or resolver state machine is introduced merely for 0.5.x.

## 8. State model

The project has distinct state layers and must not collapse them into one file or one state machine.

### Runtime state

`runtime.json` / status v2 represents operational runtime facts such as backend, adapter, lifecycle and health.

### Reconciliation/control state

`runtime/reconcile-state.json` represents desired/observed revision and convergence information used by the control plane.

The Control API may aggregate these into one response, but their ownership remains distinct:

```text
Desired / Observed / Convergence
          +
Backend / Adapter / Lifecycle / Health
          |
          v
     Control API view
```

Absence of reconciliation state remains `unknown`, not `backend=down`.

## 9. Health and failure evidence

Health is an extension of existing runtime/reconciliation state, not a second health daemon.

Conceptual fields:

```text
transport_status
jump_status
 target_status
proxy_status
overall_status
```

For direct transport, `jump_status` is `not_applicable`.

A health result must distinguish status from evidence/reason where possible:

```text
status: unknown | ready | degraded | failed | not_applicable
reason: jump_unreachable | target_unreachable | ...
last_checked: ...
```

Do not infer `target=down` when the actual evidence is only `jump=unreachable`. The system should preserve causal failure information.

## 10. Revision, desired/observed and concurrency invariants

The following semantics remain unchanged across 0.5.x:

```text
current_revision  = revision history head
desired_revision  = requested runtime revision
observed_revision = latest successfully projected/activated revision
```

`desired_revision > observed_revision` is valid after activation failure.

Mutations continue to use optimistic concurrency (`if_match_revision`) and must reject stale writes rather than silently apply last-write-wins behavior.

A mutation path is conceptually:

```text
validate
  -> authorization (when remote)
  -> revision/concurrency decision
  -> audit decision
  -> desired state
  -> pinned reconcile/activation
  -> observed state
```

The reconciler must remain pinned to the requested revision so a concurrent newer revision cannot be mistaken for success of an older request.

## 11. Locks and transaction boundaries

Existing revision/audit/lifecycle/upgrade transaction locks are infrastructure, not optional implementation details.

New 0.5.x operations must explicitly declare which state they mutate and which existing lock/transaction boundary protects it.

At minimum keep responsibilities separate:

```text
Revision lock       -> revision/head mutation
Audit lock          -> append-only audit serialization
Lifecycle lock      -> start/stop/restart/runtime lifecycle
Upgrade transaction -> installation/upgrade/restore transaction
```

Do not introduce a Web-specific lock that bypasses these boundaries.

## 12. Management plane vs data plane

They remain separate:

```text
LAN
 |
 +--> HTTPS Management -> Web Gateway -> Control API
 |
 +--> SOCKS / HTTP Data -> Backend -> Egress Path
```

Do not expose existing SOCKS/HTTP listeners publicly merely to provide LAN management. Current typed export/runtime constraints do not provide a general authenticated public SOCKS/HTTP management deployment.

The Web Gateway must not directly edit revision/runtime files, invoke `systemctl`, or manage backend processes. Its only authority is through Control API contracts.

The current Control API Unix socket remains protected (`0600`). A future Web Gateway must have an explicit local authorization/access design to call it; simply making the socket world-readable is prohibited.

## 13. Web authentication and audit durability

Initial Web security boundary:

- HTTPS/TLS
- one Admin role
- server-side session or equivalent revocable authenticated token
- CSRF protection for browser state-changing requests
- login failure/rate limiting
- secure cookie/token handling
- source ACL
- logout/revocation
- actor attribution in audit
- no secrets in audit

Remote management mutations must not claim durable success when their required audit record could not be committed. The 0.4.x compatibility behavior may remain unchanged for existing local operations; the remote management contract must define audit durability explicitly.

Web identity is initially global to the control plane, while profile remains the configuration/resource scope. Complex RBAC is deferred.

## 14. Capability evolution

Capabilities are the extension mechanism for backend-dependent features. Do not hard-code behavior solely by backend name when a capability can express it.

Future examples:

```text
supports_egress_path
supports_jump
supports_remote_dns
supports_connection_draining
supports_multi_egress
```

A backend that does not advertise a capability must not be forced into the feature. Web/UI and Control API validation should use capability metadata where appropriate.

## 15. Activation, draining and self-healing

0.4.x stop/start activation remains the default. There is no universal zero-downtime guarantee.

Connection draining is opt-in and capability-gated. A backend without the capability retains existing stop/start behavior.

Self-healing has two distinct levels:

```text
Control-plane recovery
  -> reconciliation retries / desired vs observed convergence

Data-plane recovery
  -> backend/transport restart or health recovery
```

Do not make health detection itself recursively trigger unlimited restart loops. Future recovery policy must have bounded retry/backoff, observable failure reason, stable terminal state and reset/recovery conditions.

Automatic failover is deferred until multi-egress and failure-policy semantics are separately specified.

## 16. Export/import, recovery and compatibility

Exports represent canonical configuration/revision metadata, not ephemeral runtime state:

```text
include: canonical config, references, compatible metadata
exclude: private keys, PIDs, sockets, process state, transient health
```

Import must follow:

```text
parse
 -> schema/semantic validation
 -> compatibility/migration check
 -> create revision
 -> explicit apply
```

No import operation may silently activate unvalidated configuration.

Compatibility policy:

- newer 0.5.x should preserve supported 0.4.x configurations
- forward compatibility is not assumed
- older versions must not be expected to understand newer schema fields
- downgrade requires explicit compatibility/migration handling

Schema evolution must prefer additive optional fields before breaking changes.

## 17. Profile isolation

Every new stateful object introduced in 0.5.x must answer its profile ownership explicitly.

By default:

```text
Profile
 ├─ config
 ├─ revision history
 ├─ runtime state
 ├─ audit/event context
 └─ Egress Path references
```

No accidental cross-profile secret, PID, socket, revision or health state sharing is allowed.

## 18. Deployment and platform evolution

0.5.x remains Linux-first and reuses systemd/rootless/container deployment contracts. New features must declare support for:

```text
system mode
rootless mode
container mode
```

Cross-platform runtime adapters remain later V5 work. The domain/control contracts introduced in 0.5.x must not depend on Linux-specific paths or service-manager APIs.

## 19. Error semantics

Errors must preserve the layer that failed. Do not collapse:

```text
validation failure
authorization failure
revision conflict
transport failure
jump failure
target failure
backend activation failure
reconciliation timeout
```

into one generic `backend_down` response.

Control API remains responsible for stable machine-readable error semantics; Web may translate presentation but must not invent a second error taxonomy.

## 20. Observability

Use existing operational telemetry/state. Across 0.5.x diagnostics should cover:

- control-plane health
- backend/adapter readiness
- transport/jump/target path state
- DNS path
- route/egress selection
- revision convergence
- audit/events
- recovery attempts and terminal reason
- active connection/traffic counters where already available

No full packet/content inspection is required.

## 21. Documentation authority

For 0.5.x decisions, use this precedence:

```text
V0.5-DECISIONS.zh-CN.md
        ↓
V0.5-ARCHITECTURE.zh-CN.md
        ↓
CONTROL-API.md / STATE.md / BACKENDS.md / typed-config docs
        ↓
ROADMAP.md
```

Historical/forward-looking documents must not silently override a frozen 0.5.x decision. When an implementation exposes a real contradiction, update the decision record first, then code and dependent docs.

## 22. Non-goals across 0.5.x unless separately approved

- traffic disguise or censorship/DPI evasion
- dedicated proxy-agent on Jump Host
- unlimited SSH multi-hop
- automatic load balancing by default
- VPN/WireGuard transport as an implicit dependency
- full RBAC
- full DPI/packet-content inspection
- universal zero-downtime activation
- Web-specific parallel revision/audit/reconcile implementation
- bidirectional typed/legacy configuration synchronization

## 23. Architecture acceptance criteria

A 0.5.x feature is not architecturally complete until it can answer all of these:

1. Which layer owns it?
2. Which existing 0.4.x contract does it reuse?
3. What is the canonical source of truth?
4. What state does it create or mutate?
5. Which lock/transaction protects that state?
6. What happens under concurrent mutation?
7. What happens after partial failure?
8. How does it recover, and when does recovery stop?
9. What is the compatibility behavior for old configuration?
10. What is the downgrade behavior?
11. Which capability gates it?
12. What does Web see through Control API?
13. What does the operator see when the state is unknown or partially failed?
14. How is the feature tested in system/rootless/container modes where supported?
15. Can a future implementation replace the underlying mechanism without changing the domain contract?

If a feature cannot answer these questions, it is not ready to enter implementation merely because the happy-path code is straightforward.
