# 0.5.x Architecture Decisions

> Status: design baseline, not implementation contract yet.
>
> Baseline: `main` at `932bc691a13b94abbe74bcdba7e6b498971305ed`.
>
> Versioning rule: 0.5.x is a staged evolution line. Do not require all 0.5.x capabilities to land in one release. Each minor release must remain independently testable and keep the 0.4.x compatibility boundary unless explicitly documented otherwise.

## 1. Scope and staged delivery

0.5.x extends the existing 0.4.x control plane incrementally. The full target direction includes Web/LAN management, Egress Path, SSH direct/jump transport, secret references, richer transport/egress health, recovery/portability and future connection-draining capabilities, but these are deliberately split across 0.5.x releases.

### 0.5.0 — Egress Path foundation

Keep this release small and focused on the data-plane contract:

- canonical Egress Path data model and validation
- `Backend` vs `Egress Path` responsibility boundary
- direct transport semantics
- backward-compatible integration with existing backend configuration
- typed-config to legacy-runtime projection rules
- minimal tests for config compatibility and route/egress resolution

0.5.0 does **not** require the Web UI, LAN public exposure, Jump Host support, export/import, connection draining, automatic failover or full path-health visualization.

### 0.5.1 — SSH Jump and identity/security foundations

Build on 0.5.0 without redesigning the backend layer:

- one-hop SSH Jump Host transport: Local -> Jump -> Target
- separate Jump/Target identity references
- secret-reference lifecycle and validation
- host-key/known-host handling for the new transport model
- transport/jump/target health state sufficient for diagnosis
- explicit DNS path semantics, preserving existing SSH SOCKS5 remote-DNS behavior by default

The existing `ssh-socks` lifecycle/ownership implementation remains the runtime foundation.

### 0.5.2 — Web/LAN Management Plane

Only after the underlying data-plane contracts are stable:

- Web Control Plane backed by the existing Control API contract
- LAN management listener with explicit TLS/authentication/ACL policy
- session/CSRF/rate-limit/security boundaries
- profile/backend/egress configuration UI
- validate -> diff -> apply workflow
- health/event/revision views

Web must not duplicate revision, audit, desired-state or reconcile logic.

### 0.5.3 — Recovery and operational completeness

- configuration/revision export/import
- validate-before-activation recovery workflow
- richer operational diagnostics
- audit/event visibility improvements
- deployment/integration coverage for LAN management

### 0.5.4+ — Advanced runtime capabilities

Add only when justified by real backend capability and tests:

- connection-draining capability
- multiple named egress paths and route selection
- future EgressGroup abstraction
- health-driven failover/balancing only as a later, separately specified capability

The exact patch/minor sequence may change with implementation evidence; the invariant is incremental delivery rather than one oversized 0.5.0.

## 2. Non-goals across 0.5.x unless separately specified

The 0.5.x line does not include:

- traffic disguise or censorship/DPI evasion
- a dedicated `proxy-agent` process on the Jump Host
- unlimited SSH multi-hop
- automatic egress load balancing by default
- VPN/WireGuard transport
- full RBAC
- full DPI/traffic inspection
- zero-downtime activation as a universal guarantee

## 3. Control-plane rule

All management clients enter through one control path:

```text
Browser / CLI / TUI
        |
        v
   Control API v1
        |
        +--> Revision Store
        +--> Audit Store
        +--> Desired State
        |
        v
    Reconciler
        |
        v
 Backend / Adapter
```

Web MUST NOT duplicate revision, audit, desired-state or reconcile logic and MUST NOT directly implement backend lifecycle operations.

## 4. Canonical configuration and compatibility

The canonical configuration model remains typed configuration. Legacy shell configuration is a compatibility/runtime projection, not a second source of truth:

```text
Typed Config / Revision
        |
        v
Legacy Runtime Config
        |
        v
proxy-ctl / backend / adapter
```

Do not introduce bidirectional synchronization between typed and legacy configuration.

`Backend` and `Egress Path` are separate responsibilities:

```text
Backend       = what proxy implementation is used
Egress Path   = how that backend reaches its upstream/target
```

Do not replace or redesign the existing backend model merely to introduce Egress Path. When `egress_path` is absent, existing backend-specific configuration such as `REMOTE_HOST`, `REMOTE_USER` and `REMOTE_SSH_KEY` continues to work. When `egress_path` is present, it may provide the transport/target information required by a backend through the typed configuration contract.

## 5. Network-plane separation

Management and proxy traffic are separate planes:

```text
LAN
 |
 +--> HTTPS Web Control Plane --> Control API
 |
 +--> SOCKS / HTTP Data Plane --> Egress Path
```

No blanket `0.0.0.0` exposure. Listener binding, ACL and authentication are explicit configuration concerns.

The current typed legacy exporter still rejects public SOCKS/HTTP exposure because the legacy runtime does not yet implement an authenticated public deployment policy. Therefore Web/LAN management must not be implemented by simply making existing SOCKS/HTTP listeners public.

## 6. Egress Path model

Jump Host is modeled as transport/path information rather than as a new backend:

```text
Backend
  |
  +--> Transport
        |
        +--> direct
        |
        +--> jump
              |
              +--> Jump
              +--> Target
```

Conceptual model:

```yaml
egress_path:
  transport: ssh
  jump:
    host: ...
    port: ...
    user: ...
    identity: ...
    known_hosts: ...
  target:
    host: ...
    port: ...
    user: ...
    identity: ...
    known_hosts: ...
```

The first implementation supports one jump hop only: Local -> Jump -> Target.

The backend generates SSH `ProxyJump`/equivalent invocation details. Raw command-line `ProxyJump` strings are not the primary configuration model.

## 7. Jump Host role

The default architecture is:

```text
LAN Client
   |
   v
proxy-agent
   |
   | SSH
   v
Jump Host (OpenSSH)
   |
   | SSH forwarding
   v
Target VPS
   |
   v
Internet
```

The Jump Host does not need a separate `proxy-agent` daemon in 0.5.x. A future relay/gateway role is only justified if the intermediate node later owns policy, accounting, failover, VPN/NAT orchestration or multiple egresses.

## 8. Identity and secrets

Jump and Target identities should be independently addressable. Prefer:

```text
local -> Jump : key-A
local/transport -> Target : key-B
```

over a universal key.

Web/API configuration uses secret references rather than private-key material. UI/API responses may expose configured state, fingerprint and validation status, but never private key contents.

Secret lifecycle is:

```text
reference -> existence/readability check -> runtime resolution -> backend
```

The secret model is introduced incrementally; existing `ssh-socks` key handling must remain functional while references are added.

## 9. Authentication and Web security

The LAN Web Control Plane requires an explicit security boundary:

- HTTPS/TLS
- authentication
- session lifecycle
- CSRF protection for browser state-changing operations
- login failure/rate limiting
- secure cookie/token handling
- ACL/source restrictions
- audit actor attribution
- logout/revocation
- no secrets in audit events

The initial Web implementation uses a single Admin role; RBAC remains future scope.

## 10. Egress health model

Do not collapse all failures into `backend=down`. Track path-level state as an extension of existing runtime/reconciliation state rather than creating a second health system:

```text
transport_status
jump_status
target_status
proxy_status
overall_status
```

`jump_status` is `not_applicable` for direct transport.

Example:

```json
{
  "transport": "ready",
  "jump": "ready",
  "target": "unreachable",
  "proxy": "degraded",
  "overall": "degraded"
}
```

The existing runtime state file remains the state publication point; Web reads/visualizes this state instead of inventing a parallel state store. Existing `unknown` state must remain distinct from an actual transport/backend failure.

## 11. DNS semantics

Egress routing must make DNS path explicit. Existing SSH SOCKS5 behavior uses `socks5h`, so remote DNS semantics are preserved unless a profile explicitly selects another supported mode.

Minimum conceptual policy:

```text
dns_mode: local | remote
```

Route -> Egress -> DNS behavior must be diagnosable.

## 12. Activation and connection draining

Current 0.4.x activation remains stop/start and does not promise universal zero downtime.

Connection draining is a later capability, not a prerequisite for the initial Egress Path/Web releases. Only backends that explicitly advertise a `connection_draining` capability may use drain-aware activation; other backends retain existing stop/start behavior.

## 13. Multi-egress boundary

Multiple named Egress Paths may be introduced later in 0.5.x once the single-path contract is stable:

```text
route A -> egress-us
route B -> egress-jp
default -> egress-us
```

Automatic balancing, weighted selection and health-driven failover are deferred until their semantics and failure handling are specified separately.

Future shape:

```text
EgressGroup
  -> members
  -> health
  -> selection policy
```

## 14. Recovery and portability

Export/import is a later 0.5.x operational feature rather than a prerequisite for the first Egress Path release.

When implemented, exports must not contain private-key material. Imported configuration follows the existing validate -> revision -> apply path.

## 15. Observability

Web should expose existing operational state rather than create a second telemetry system. Across 0.5.x, diagnostics should cover:

- control-plane health
- backend/adapter readiness
- SSH transport state
- Jump Host reachability
- Target reachability
- DNS resolution path
- route/egress selection
- recent audit/events
- revision convergence
- active connection/traffic counters where already available

Full packet/content inspection is out of scope.

## 16. Security boundary for the Jump Host

The Jump Host should be treated as a hardened SSH forwarding boundary. The project may document least-privilege OpenSSH configuration, source restrictions, key separation, host-key verification and disabled interactive access as deployment guidance.

This is security hardening, not traffic disguise or censorship-evasion behavior.

## 17. Dependency impact on existing 0.4.x

Expected reuse:

```text
Control API
Revision Store
Audit Store
Desired/Observed State
Reconciler
Backend lifecycle
Backend capabilities
Adapter compatibility
Profile isolation
SSH SOCKS5 backend
Health framework
```

The primary new contracts are introduced incrementally:

```text
0.5.0  Egress Path / Transport boundary
0.5.1  Jump / Secret Reference / Path Health / DNS policy
0.5.2  Web Auth/Session / Listener Security / LAN management
0.5.3  Export/Import / Recovery / richer diagnostics
0.5.4+ Connection Draining / Multi-egress / later selection policies
```

The implementation must avoid embedding these concerns directly into `proxy-ctl` beyond the existing Linux reference behavior; typed configuration and stable contracts remain the preferred extension point.

## 18. Implementation order inside the 0.5.x line

### 0.5.0

1. Trace the current config -> profile -> backend -> route -> reconciler -> Control API call chain.
2. Add Egress Path typed data model and validation.
3. Define direct transport semantics.
4. Preserve legacy backend behavior when `egress_path` is absent.
5. Add focused config/revision/reconcile smoke coverage.

### 0.5.1

1. Add one-hop SSH Jump semantics.
2. Add identity/secret references without exposing key material.
3. Add path-level health state and diagnostics.
4. Define DNS policy while preserving current ssh-socks defaults.

### 0.5.2

1. Extend Control API only where the existing contract cannot represent the new configuration/state.
2. Add authenticated HTTPS Web management.
3. Keep LAN management and data-plane listeners separate.
4. Add Web integration and security tests.

### 0.5.3+

1. Add export/import and recovery.
2. Add optional advanced observability.
3. Introduce connection draining only behind an explicit backend capability.
4. Introduce multiple named egress paths only after the single-path contract is stable.
5. Add release gates and compatibility documentation for every 0.5.x increment.

This staged order minimizes Web/API rework and keeps the existing 0.4.x control-plane authority intact.
