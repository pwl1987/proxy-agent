# 0.5.0 Architecture Decisions

> Status: design baseline, not implementation contract yet.
>
> Baseline: `main` at `932bc691a13b94abbe74bcdba7e6b498971305ed`.

## 1. Scope

0.5.0 is not merely a Web UI release. It extends the existing 0.4.x control plane with:

- Web Control Plane
- LAN management/data-plane exposure with explicit security boundaries
- Egress Path abstraction
- SSH direct/jump transport
- Jump Host as a network path node, not a second control agent
- Secret references
- richer transport/egress health state
- configuration export/import and recovery boundaries
- future-compatible connection draining capability

The existing Control API, revision store, audit store, desired/observed state and reconciler remain authoritative.

## 2. Non-goals

0.5.0 does not include:

- traffic disguise or censorship/DPI evasion
- a dedicated `proxy-agent` process on the Jump Host
- unlimited SSH multi-hop
- automatic egress load balancing
- automatic egress failover
- VPN/WireGuard transport
- full RBAC
- full DPI/traffic inspection
- zero-downtime activation as a universal guarantee

## 3. Control-plane rule

All management clients enter through one control path:

```text
Browser / CLI / TUI
        |
        v
   Control API v1
        |
        +--> Revision Store
        +--> Audit Store
        +--> Desired State
        |
        v
    Reconciler
        |
        v
 Backend / Adapter
```

Web MUST NOT duplicate revision, audit, desired-state or reconcile logic and MUST NOT directly implement backend lifecycle operations.

## 4. Network-plane separation

Management and proxy traffic are separate planes:

```text
LAN
 |
 +--> HTTPS Web Control Plane --> Control API
 |
 +--> SOCKS / HTTP Data Plane --> Egress Path
```

No blanket `0.0.0.0` exposure. Listener binding, ACL and authentication are explicit configuration concerns.

## 5. Egress Path model

Jump Host is modeled as transport/path information rather than as a new backend:

```text
Backend
  |
  +--> Transport
        |
        +--> direct
        |
        +--> jump
              |
              +--> Jump
              +--> Target
```

Conceptual model:

```yaml
egress_path:
  transport: ssh
  jump:
    host: ...
    port: ...
    user: ...
    identity: ...
    known_hosts: ...
  target:
    host: ...
    port: ...
    user: ...
    identity: ...
    known_hosts: ...
```

0.5.0 supports one jump hop only: Local -> Jump -> Target.

The backend generates SSH `ProxyJump`/equivalent invocation details. Raw command-line `ProxyJump` strings are not the primary configuration model.

## 6. Jump Host role

The default architecture is:

```text
LAN Client
   |
   v
proxy-agent
   |
   | SSH
   v
Jump Host (OpenSSH)
   |
   | SSH forwarding
   v
Target VPS
   |
   v
Internet
```

The Jump Host does not need a separate `proxy-agent` daemon in 0.5.0. A future relay/gateway role is only justified if the intermediate node later owns policy, accounting, failover, VPN/NAT orchestration or multiple egresses.

## 7. Identity and secrets

Jump and Target identities should be independently addressable. Prefer:

```text
local -> Jump : key-A
local/transport -> Target : key-B
```

over a universal key.

Web/API configuration uses secret references rather than private-key material. UI/API responses may expose configured state, fingerprint and validation status, but never private key contents.

Secret lifecycle must cover:

```text
reference -> existence/readability check -> runtime resolution -> backend
```

## 8. Authentication and Web security

The LAN Web Control Plane requires an explicit security boundary:

- HTTPS/TLS
- authentication
- session lifecycle
- CSRF protection for browser state-changing operations
- login failure/rate limiting
- secure cookie/token handling
- ACL/source restrictions
- audit actor attribution
- logout/revocation
- no secrets in audit events

0.5.0 starts with a single Admin role; RBAC remains future scope.

## 9. Egress health model

Do not collapse all failures into `backend=down`. Track at least:

```text
transport_status
jump_status
target_status
proxy_status
overall_status
```

Example:

```json
{
  "transport": "ready",
  "jump": "ready",
  "target": "unreachable",
  "proxy": "degraded",
  "overall": "degraded"
}
```

Health must remain compatible with existing backend/adapter readiness and desired/observed revision semantics.

## 10. DNS semantics

0.5.0 must make DNS path explicit. Existing SSH SOCKS5 behavior uses `socks5h`, so remote DNS semantics should be preserved unless a profile explicitly chooses another supported mode.

Minimum conceptual policy:

```text
dns_mode: local | remote
```

Route -> Egress -> DNS behavior must be diagnosable.

## 11. Activation and connection draining

Current 0.4.x activation remains stop/start and does not promise universal zero downtime.

0.5.0 may introduce a capability such as:

```text
connection_draining
```

but only backends that explicitly advertise it may use drain-aware activation. Other backends retain existing stop/start behavior.

## 12. Multi-egress boundary

0.5.0 may define multiple named Egress Paths and route rules that select them:

```text
route A -> egress-us
route B -> egress-jp
default -> egress-us
```

Automatic balancing, weighted selection and health-driven failover are deferred.

Future shape:

```text
EgressGroup
  -> members
  -> health
  -> selection policy
```

## 13. Recovery and portability

Because 0.5.0 introduces more mutable control-plane state, provide configuration/revision export and import with validation before activation.

Exports must not contain private-key material. Rollback remains revision-based; imported configuration should follow the existing validate -> revision -> apply path.

## 14. Observability

Web should expose existing operational state rather than create a second telemetry system. 0.5.0 should make it possible to diagnose:

- control-plane health
- backend/adapter readiness
- SSH transport state
- Jump Host reachability
- Target reachability
- DNS resolution path
- route selection
- recent audit/events
- revision convergence
- active connection/traffic counters where already available

Full packet/content inspection is out of scope.

## 15. Security boundary for the Jump Host

The Jump Host should be treated as a hardened SSH forwarding boundary. The project may document least-privilege OpenSSH configuration, source restrictions, key separation, host-key verification and disabled interactive access as deployment guidance.

This is security hardening, not traffic disguise or censorship-evasion behavior.

## 16. Dependency impact on existing 0.4.x

Expected reuse:

```text
Control API
Revision Store
Audit Store
Desired/Observed State
Reconciler
Backend lifecycle
Backend capabilities
Adapter compatibility
Profile isolation
SSH SOCKS5 backend
Health framework
```

The primary new contracts are:

```text
Web Auth/Session
Listener Security
Egress Path
Transport
Secret Reference
Egress Health
DNS Policy
Connection Draining capability
Export/Import
```

The implementation must avoid embedding these concerns directly into `proxy-ctl` beyond the existing Linux reference behavior; typed configuration and stable contracts remain the preferred extension point.

## 17. Implementation order

Before building the Web UI, settle these contracts in order:

1. Egress Path data model and validation
2. Transport direct/jump semantics
3. Secret reference and identity model
4. Listener/security model
5. Egress/transport health state
6. DNS policy semantics
7. Connection-draining capability boundary
8. Export/import and recovery
9. Control API extensions
10. Web UI implementation
11. LAN deployment and integration tests
12. release gates and 0.5.0 documentation

This order minimizes Web/API rework and preserves the existing 0.4.x control-plane authority.
