# 0.5.x 总体架构决断

> 状态：冻结的设计决断，作为 0.5.x 后续实现的共同前提。
>
> 基线：`main@932bc691a13b94abbe74bcdba7e6b498971305ed`。
>
> 原则：0.5.x 是连续演进线，不要求所有能力集中在 0.5.0。每个版本必须可独立测试、可回归、可发布，并尽量保持 0.4.x 行为兼容。

## 1. 总体版本边界

### 0.5.0 — Egress Path foundation

只解决“代理如何到达上游/目标”的基础数据合同：

- `egress_path` typed model
- Backend 与 Egress Path 职责边界
- direct transport
- 旧 backend-specific SSH 配置兼容
- typed config -> legacy runtime 单向投影
- 配置、revision、reconcile、route/egress resolution 基础测试

明确不在 0.5.0 实现：Web、LAN 管理、Jump Host、secret 生命周期、export/import、connection draining、自动 failover/balancing。

### 0.5.1 — Jump + Identity + Path Health

- 单跳 SSH：Local -> Jump -> Target
- Jump/Target 独立 identity/known_hosts references
- secret-reference 生命周期与验证
- transport/jump/target path health
- DNS path policy
- 继续复用现有 `ssh-socks` lifecycle / ownership contract

### 0.5.2 — Web/LAN Management

- Web 管理面
- LAN HTTPS listener
- authentication/session/CSRF/rate-limit/ACL
- profile/backend/egress configuration UI
- Validate -> Diff -> Apply
- health/event/revision views

### 0.5.3 — Recovery / Operations

- export/import
- validate-before-activation recovery
- 更完整 diagnostics
- LAN deployment/integration coverage

### 0.5.4+ — Advanced Runtime

- connection draining capability
- multiple named egress paths
- route -> egress selection
- 后续 EgressGroup / failover / balancing（另行定义后再实现）

## 2. Core responsibility boundary

现有 backend 模型不重写。

```text
Backend
= 使用什么代理实现

Egress Path
= 这个代理怎样到达 upstream / target
```

Backend 继续负责 backend-specific process/lifecycle/endpoint/capabilities；Egress Path 负责 transport/target/jump 等路径信息。

只有声明支持 Egress Path 的 backend 才消费该字段。未声明支持的 backend 不得静默忽略非空 `egress_path`，validation 必须明确报错。

## 3. Canonical configuration / revision

typed configuration 是 canonical source of truth。

```text
Typed Config
    ↓
Revision Store
    ↓
Reconciler
    ↓
Legacy Runtime Config
    ↓
proxy-ctl / backend / adapter
```

禁止 typed 与 legacy 双向同步。

Revision history 保存完整 canonical typed config；secret 只保存 reference，不保存 private-key material。

`schema_version` 继续独立于 release version。0.5.x 采用向后兼容的增量扩展，除非出现真正 breaking change，不因为每个 0.5.x 小版本机械递增 schema version。

## 4. Egress Path canonical model

0.5.x 统一使用以下概念名：

```yaml
egress_path:
  transport: ssh
  mode: direct | jump
  target:
    host: ...
    port: ...
    user: ...
    identity_ref: ...
    known_hosts_ref: ...
  jump:
    host: ...
    port: ...
    user: ...
    identity_ref: ...
    known_hosts_ref: ...
  dns_mode: local | remote
```

字段决断：

- `target`：最终 SSH/egress target，不表示 HTTP/SOCKS 客户端目标。
- `jump`：可选中间 SSH 节点；0.5.x 最多一跳。
- `identity_ref`：secret/identity reference，不是私钥内容。
- `known_hosts_ref`：known_hosts reference/path abstraction，不在模型中塞入整个文件内容。
- `mode=direct` 时 `jump` 不存在。
- `mode=jump` 时 `jump` 与 `target` 都必须存在。
- 0.5.0 只要求 `mode=direct` 可运行；jump schema 可以先冻结、后在 0.5.1 激活。
- `transport` 不是 raw command line；SSH `ProxyJump` 等 invocation detail 由 transport/backend implementation 生成。

## 5. Legacy compatibility decision

当前 0.4.x SSH SOCKS backend 已有 `REMOTE_HOST`、`REMOTE_USER`、`REMOTE_PORT`、`REMOTE_SSH_KEY` 等 backend-specific 配置。

0.5.x 保留兼容路径：

```text
没有 egress_path
    ↓
继续使用现有 backend.options / legacy variables
```

而：

```text
有 egress_path
    ↓
由 typed layer 解析并向 backend 提供所需 transport/target 参数
```

不能在 0.5.0 强制已有 profile 迁移到新格式。

禁止出现两个同时生效且没有优先级定义的 target source。

当 `egress_path` 与旧 backend-specific SSH target 同时存在时，validation 必须拒绝歧义，而不是猜测覆盖顺序。

## 6. Profile boundary

Profile 仍是完整控制上下文：

```text
profile
 ├─ config
 ├─ state dir
 ├─ log dir
 └─ revision store
```

Egress Path 属于 profile configuration；不同 profile 不共享 mutable runtime state。

现有 profile context 的 resolved paths 必须继续向 downstream commands 传递，禁止二次追加 profile 名称。

## 7. Routing decision

现有 routing contract 不推翻：`ROUTE_RULES` 仍按 priority 处理 direct/proxy，legacy direct domain/CIDR 列表继续作为兼容能力。fileciteturn20file0L9-L9

0.5.0 不改变“route 决定 direct/proxy”的既有语义。

0.5.4+ 才把“proxy -> 哪个 Egress Path”作为增量选择层：

```text
request
  ↓
route rule
  ↓
direct OR proxy
          ↓
     egress selection
          ↓
      Egress Path
```

因此不能把 Egress Path 选择偷偷混入当前 `DIRECT/PROXY` action 的含义。

## 8. DNS decision

DNS 是 egress behavior 的一部分，但不是独立的大型 subsystem。

统一概念：

```text
dns_mode: local | remote
```

对于现有 `ssh-socks`，当前 `socks5h` 体现 remote DNS 语义，因此 0.5.x 默认必须保持兼容行为；改变 DNS path 必须是显式配置。

## 9. State model

继续使用现有 revision/reconcile/runtime state，不建立第二套状态机。

冻结以下语义：

```text
current_revision
= revision history head

desired_revision
= 控制面要求 runtime 达到的 revision

observed_revision
= 最近成功投影/激活的 revision
```

因此：

```text
desired_revision > observed_revision
```

在 activation failure 时是合法中间态。

Path health 是 runtime/reconciliation state 的扩展，不另建 daemon/state store。

状态至少按：

```text
transport_status
jump_status
 target_status
proxy_status
overall_status
```

直接路径时 `jump_status=not_applicable`。

`unknown` 必须与 `failed/unreachable` 区分。

## 10. Backend capability decision

现有 backend capability contract 继续作为动态能力来源，而不是在 Control API 中写死 backend 名称分支。

0.5.x 新能力全部采用 capability gate：

```text
Egress Path support
Jump transport support
connection_draining
```

没有 capability 的 backend：

- 不得被强行套用新行为
- validation 必须给出清晰错误
- 继续执行原有 lifecycle/endpoint contract

## 11. Jump Host decision

Jump Host 在 0.5.x 中是 OpenSSH path node，不运行第二个 `proxy-agent` 控制进程。

```text
proxy-agent
   ↓ SSH
Jump Host
   ↓ SSH forwarding
Target
```

0.5.1 只支持一跳。

禁止在配置中开放无限 `ProxyJump` 字符串作为通用 multi-hop DSL。

Jump Host 安全策略属于部署/transport security：最小权限、source restriction、独立 key、host-key verification、禁止不必要的 interactive access。

不实现 traffic disguise、DPI evasion 或其它规避审查行为。

## 12. Identity / Secret decision

0.5.x 不把 secret 当作普通 config string。

canonical model 使用 reference：

```text
identity_ref
known_hosts_ref
```

生命周期：

```text
reference
  ↓
existence / readability validation
  ↓
runtime resolution
  ↓
backend/transport
```

API/UI 可显示：

- configured/unconfigured
- fingerprint（适用时）
- validation status

不可显示或写入 audit/revision：private-key material。

Jump 与 Target 默认允许使用不同 identity reference；不要求所有路径共用一个 key。

## 13. Control API decision

现有 Control API v1 继续作为唯一后端控制合同：

```text
CLI / TUI / Web
       ↓
Control API
       ↓
Revision / Audit / Desired State
       ↓
Reconciler
       ↓
Backend / Adapter
```

0.5.x 原则：

- API v1 尽量 additive extension
- 不在 Web 中重复 revision/audit/reconcile/lifecycle
- 不让 Web 直接写 config 文件
- 不让 Web 直接调用 backend/systemctl
- 真正 breaking API contract 才考虑新 API version；不因 Web 自己造页面就升版

当前 API 已支持 profile context、revision concurrency、rollback、runtime operations，因此新功能优先扩展已有 endpoint semantics，而不是平行造新的 control path。fileciteturn45file0L2-L2

## 14. Web / LAN decision

Web 管理面与 Data Plane 永远分离：

```text
LAN
 ├─ HTTPS management → Web gateway → local Control API
 └─ SOCKS/HTTP data → proxy backend → Egress Path
```

现有 Control API 默认 Unix socket `0600`，远程 HTTP 不属于当前 Control API 合同。fileciteturn45file0L2-L2

因此 Web 不等于把现有 Control API 直接开放到 LAN。

Web gateway 是 remote management boundary；Control API 仍保持本地 privileged control boundary。

LAN management 默认 deny-by-default，必须同时具备适用的 TLS、authentication、session、CSRF、rate limiting 和 ACL policy。

现有 typed legacy exporter 目前会拒绝 public SOCKS/HTTP exposure，因为 legacy runtime 尚无 authenticated public deployment policy。fileciteturn22file0L2-L2

因此 0.5.2 不通过“把 SOCKS/HTTP bind 改成 `0.0.0.0`”来实现 Web/LAN 管理。

## 15. Web security baseline

0.5.2 第一版只定义一个 `Admin` role，不做完整 RBAC。

必须具备：

```text
TLS
Authentication
Session lifecycle
CSRF
Login failure/rate limit
Secure cookie/token handling
Source ACL
Audit actor attribution
Logout/revocation
```

浏览器不能获得 root/control-socket credentials，也不能直接访问 Unix socket。

## 16. Activation / draining decision

现有 0.4.x activation 仍是受控 stop/start，不承诺 universal zero-downtime。

0.5.x 不改变这一事实。

`connection_draining` 作为未来 backend capability：

```text
capability absent → 旧 stop/start
capability present → 可使用 drain-aware activation
```

Web 不得把所有 backend 的 apply 宣称为“无感切换”。

## 17. Multi-egress decision

多 Egress Path 是后置能力，不进入 0.5.0/0.5.1 的 runtime complexity。

冻结未来抽象名：

```text
named Egress Path
        ↓
route selection
        ↓
(optional later)
EgressGroup
```

0.5.4+ 才考虑自动 failover / balancing，并且必须先单独冻结：selection policy、health interaction、retry semantics、connection impact、audit semantics。

## 18. Export / Recovery decision

export/import 属于 0.5.3 operational layer，不阻塞早期 Egress Path。

原则：

```text
import
 ↓
validate
 ↓
create revision
 ↓
explicit apply
```

禁止 import 直接覆盖 live runtime。

export 不包含 private-key material，只包含可恢复的 canonical configuration + references + 必要 metadata。

## 19. Observability decision

继续复用现有 runtime state、health、audit、events、metrics；不造第二 telemetry plane。

0.5.x 应逐步可诊断：

```text
control health
backend/adapter readiness
transport
jump reachability
target reachability
DNS path
route/egress selection
revision convergence
audit/events
```

不存在数据的指标显示 `unknown` / `not_applicable`，不能伪造为 healthy。

## 20. Error / concurrency decision

继续沿用现有 Control API semantics：

```text
422 invalid_config
409 revision_conflict
503 activation_failed
```

revision store 已使用 profile-local lock、revision head 与 `if_match_revision` 做并发保护；0.5.x 不绕过 revision store 直接写 desired/runtime state。fileciteturn43file0L2-L2

任何新的 mutating control flow 都必须有明确的：

```text
validation point
concurrency point
revision impact
audit event
activation outcome
```

## 21. Backward-compatibility decision

0.5.x 的默认目标是：

```text
0.4.x config
   ↓
0.5.x runtime
   ↓
行为保持兼容
```

尤其保护：

- 既有 profiles
- existing backend lifecycle
- managed/unmanaged ownership
- route semantics
- revision/audit semantics
- `ssh-socks` process identity and port ownership
- local Control API behavior

任何必须改变的行为都必须作为单独的 release note / migration rule，而不是隐式改变。

## 22. Implementation discipline

严格执行以下顺序：

```text
0.5.0
Egress model → validation → direct transport → compatibility

0.5.1
Jump → identity/secret → path health → DNS

0.5.2
Control API additive extensions → Web gateway → LAN security

0.5.3
Recovery → export/import → diagnostics

0.5.4+
Advanced capabilities only after explicit capability contract
```

不要为了“提前支持未来功能”在当前版本提前引入运行时分支、后台 daemon 或新的 state store。

## 23. Final arbitration

截至当前代码与上述决断，0.5.x 后续概念统一为：

```text
Backend
  └─ uses → Egress Path
             ├─ Transport
             ├─ Target
             ├─ optional Jump
             └─ DNS policy

Control API
  ├─ Revision
  ├─ Audit
  ├─ Desired State
  └─ Reconciler

Runtime State
  ├─ Backend / Adapter
  ├─ Revision convergence
  └─ Transport / Jump / Target path health

Web / LAN
  └─ management gateway only
```

以后出现的新需求，必须先回答属于以下哪一层：

```text
Config
Backend
Egress Path / Transport
Routing
Runtime State / Health
Control API
Web / Management
Deployment / Security
```

不能跨层偷偷增加第二套数据结构、状态机或控制入口。
